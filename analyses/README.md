## Table S3 and report synchronisation

Step 06 Task 7 writes the following to `data/06-figs2-lifestyle/quality_sensitivity/`:

- `Table_S3a_quality_counts.csv`: quality-group counts.
- `Table_S3b_quality_sample_fractions.csv`: quality-by-sample summaries.
- `Table_S3_comparison.csv`: four-sample comparison.
- `Table_S3_source_vOTU_TPM.csv`: 962 source vOTUs and their TPM values.

Task 8 preserves these four Task 7 CSVs and adds:

- `Table_S3_taxonomic_coverage.csv`: 36 rows of assignment counts and count fractions at class, order, family and genus ranks: four primary-catalogue overview rows plus four samples × two abundance subsets (Abundant and Rare) × four ranks.
- `Table_S3_vOTU_quality_taxonomy.csv`: 962 vOTU rows with quality, predicted strategy, representative-contig metadata, taxonomy and each sample's TPM, relative TPM and abundance group.

Taxonomic coverage uses the number of vOTUs in the indicated catalogue or sample-specific subset as its denominator. Ranks are evaluated independently; missing labels and rank placeholders are treated as Unclassified, with original labels retained in the detail table. These count fractions are separate from the TPM-weighted predicted temperate fractions in Task 7.

Abundance groups are assigned separately in BS, SA, IA and DA using each sample's total TPM across all 962 primary representatives: Abundant ≥0.01, Rare >0 and <0.001, Intermediate ≥0.001 and <0.01, and Not detected =0 relative TPM. A vOTU can have different groups in different samples, so sample counts must not be summed as unique catalogue counts. Table S3 uses only the 962-vOTU primary catalogue; Figure S2 continues to use the 2,488-vOTU discovery catalogue.

All six CSVs are generated by step 06 and tracked for numerical inspection. Task 8 also exports `Table_S3_quality_taxonomy.xlsx` in the same directory, with seven sheets: Quality counts, TPM comparison, Taxonomic coverage, vOTU data, AMG curation, AMG evidence and Notes. The generated workbook remains a local output.

When updating a notebook, also update its tracked Markdown report and referenced preview images. Use `quarto render <notebook.qmd> --to gfm` for GitHub reports. Temporary TIFFs and HTML libraries are not required in Git. Figure 2b intentionally has no fixed random seed; rerun rarefaction curves may differ.

## Candidate-AMG evidence in Table S3

`R/amg_curation.R` builds an ORF-level inventory directly from the primary TSE and the archived inputs in `data/00-raw/d04-amg-curation/`. Step 04 writes the evidence CSVs to `data/04-fig4-heatmap/amg_curation/`; step 06 calls the same helper when assembling Table S3. The helper does not query KEGG, rerun structures or regenerate figures.

There are 167 candidate ORFs on 124 primary-catalogue vOTUs. All receive annotation/context checks; 20 have additional targeted computational assessments. Original labels, raw evidence and current interpretations remain distinct. No experimentally established auxiliary role is asserted. PHROG records with incompatible query lengths are retained for provenance but excluded from functional assessment; reference-proxy evidence is explicitly labelled.

To regenerate the complete Table S3 while preserving the author's formatting, footnotes and Notes, run from the repository root:

```bash
Rscript analyses/R/export_table_s3_amg.R analyses /path/to/existing_Table_S3.xlsx /path/to/new_Table_S3.xlsx
```

The exporter executes only the two Table S3 chunks from step 06, refreshes the existing quality/taxonomy data blocks, and adds or replaces the AMG sheets. It validates all exported data blocks against the regenerated results. Figures and network queries are not run. Keep the original column headers and block positions in the author-formatted workbook; a changed layout stops the export for review.

Use a different output path. The original workbook is never overwritten. See `data/00-raw/d04-amg-curation/README.md` for the evidence protocol, source checks and limitations. The two R files, archived CSV inputs and their manifests must accompany the updated 04/06 notebooks; uploading the QMD files alone is insufficient.
